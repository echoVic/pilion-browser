## 决策问题

十条本地特性分支（多会话、外部 MCP/CLI、定时任务、面板重设计、输入框增强、后台标签渲染、E2E 稳定性）已经堆叠集成为一条线，但尚未进入 main。问题是：**这条改变两条既有硬边界的集成线，应该整体作为一个 minor 发布，还是拆成多个 patch 顺序发布？**

## 背景与驱动力

| 驱动力                      | 说明                                                                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 功能已完整成型且互相耦合    | 定时任务依赖多会话并行连接；后台标签真实渲染为多会话服务；会话级权限模式与多会话是同一组状态机重构。各流只在「集成形态」下被测试过  |
| main 已停滞且不再是分支祖先 | main @ 0.1.10 之后仅新增 README 重写与设置页 CSS 修复两个提交；拖得越久，1664 行 main.ts 差异与 1790 行 style.css 差异的冲突税越高  |
| 产品核心价值跃迁            | 从「一个活跃 Agent」变为「最多 4 个会话并行 + 无人值守定时任务 + 外部程序可控」，语义上是 minor 而非 patch                          |
| 安全边界扩大需要显式决策    | 新增对外 Unix socket 信任面，并把单租户 ACL 翻转为按会话/principal 隔离，不能以 patch 悄悄发布                                      |
| 证据基础较好但不完整        | 类型检查、lint、934 条单测在集成 HEAD 全绿，E2E 扩到 76 条；但全部基于确定性 fixture，真实模型验收停留在 2026-09-07 的单 Agent 链路 |

## 决策

**作为 0.2.0 单个 minor 整体发布集成 HEAD，但必须通过下文三道发布闸口。** 唯一允许在临门前摘下的子系统是外部 MCP/CLI 通道（它与多会话耦合最浅），摘下时其余内容照发，外部通道延后到 0.3.0。

发布方式：以 merge commit 合并（main 已有两个分支外提交，无法快进），合并时保留堆叠线上各流的 merge commit 作为评审与回溯边界。

## 被否决的备选

| 备选                          | 否决理由                                                                                                                                                        |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 拆成 0.1.11–0.1.15 多个 patch | 需要重放 79 个堆叠提交并为每个切片补从未验证过的组合测试，估计 2–4 个工作日，安全收益为负；且多会话改变文档化的「一个活跃 Agent」硬边界，按语义化版本属于 minor |
| 无闸口直接合并发布            | 外部 socket 是新的本机信任边界，ACL 不变量从单会话翻转为多主体隔离，934 条 fixture 测试证明不了真实模型行为与本机攻击面，风险不可接受                           |
| 继续堆叠、等更多功能再发      | main.ts 已从 3768 行膨胀到 4946 行，分支越拖冲突越大；定时任务等代码长期只存在于本地分支，没有真实用户反馈，风险只会累积                                        |

## 后果

### 正面

- 一次释放并行 Agent（核心产品能力）、定时自动化、外部控制通道、面板交互重做四类价值。
- 所有新能力默认安全姿态保守：外部通道默认关闭；定时任务默认「操作前确认」，无人审批 60 秒自动拒绝；录制保持标签级互斥而非全局锁。
- 测试资产显著增加：单测 55 → 75 文件（约 380 → 934 用例），E2E 55 → 76 用例；新增测试 profile 防误写守卫。

### 负面

- 单版本变更面大，回归定位需要按流分组的 merge commit 辅助。
- [main.ts](file://../../src/main/main.ts) 从 3768 行增至 4946 行（+31%），IPC 装配仍是上帝文件，尽管已抽出 `session-runtime.ts`、`external/`、`schedule/`、`composer/`、`panel/` 等模块。
- 多会话对用户是新心智模型（会话级权限、后台标签、4 连接上限），需要发行说明讲清。
- 旧数据迁移面增加：全局权限模式迁移为会话级；旧版外部共享 token 配置启动时删除并写迁移审计。

## 可逆性

- **撤销成本（双向门）**：桌面应用 + 自动更新，发布后可用 0.2.1 patch 回退单个子系统；三个新风险面各有开关或默认值——外部通道默认关闭、定时任务默认 ask、并发上限 4 是常量，可热修降低。
- **重新考虑触发条件**：
  1. E2E 三条关键新断言组（多会话隔离、定时任务 ask 超时、外部 token 吊销）无法在合并窗口内转绿；
  2. 外部通道安全复审发现 socket/token 模型存在高危问题——触发「摘掉外部通道」的预案；
  3. 真实模型冒烟显示多会话下适配器行为不稳定（连接串扰、会话恢复错乱）。
